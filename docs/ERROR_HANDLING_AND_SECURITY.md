# Error handling and security notes

The application uses Django CSRF middleware, password hashing/authentication, session middleware, standard password validators in settings, Django form validation, signed activation/reset tokens, and `login_required` on many account views. The account order detail view is now owner-scoped. Local settings use explicit localhost hosts, local files, console email and a demo-only fallback secret.

Confirmed follow-up risks: cart updates/removals use GET routes, variation parsing ignores invalid values, and totals use float fields in order records. Some sensitive endpoints lack visible decorators, reset/change password views do not call password validators, login redirect parsing is unsafe/fragile, broad catches hide defects, and user profile lookup can fail when data is inconsistent. The local demo-order endpoint never takes payment; its database operations are atomic and it checks order ownership and stock, but email errors after commit are not handled gracefully. Several product and order lookups should return 404 rather than server errors.

The local fallback `SECRET_KEY` is public by design and must never be used for deployment. To configure SMTP locally, set `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend` and provide mail settings in an ignored `.env`; otherwise the console backend is convenient. Never put real credentials, production customer data or real payment information in this demo. Before deployment, replace local configuration with managed secrets, HTTPS, secure cookie settings, restricted hosts, vetted storage/email, thorough access controls and a real provider verification flow.
